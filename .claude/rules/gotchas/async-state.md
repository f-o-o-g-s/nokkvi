# Gotchas: Optimistic UI & Race Conditions

- **Tick handler race**: 10 Hz tick can overwrite optimistic state with stale backend state — use pending flags to prevent reversion before API response.
- **UI stale-drop counters are `StaleDropGen`** (`src/state/stale_drop.rs`): work captures `current()` when dispatched, its result handler checks `accepts(captured)`, and every new dispatch calls `bump()`. Messages carry the captured value as a plain `u64`. The counters only count up, across logout too: iced Tasks outlive a session reset, so a counter restarted at 0 re-mints a value a pre-logout task captured and accepts its stale result. There is no setter, but `Default` still builds a zeroed one: a group holding one resets through a `reset_for_session()` that bumps it in place or rebuilds with `carried_forward()`, never by replacing the group with `Default::default()`. `LyricsState` (holding `load_epoch`) is kept whole at logout: it follows the now-playing track. Counters with their own shape: `ProgressiveQueueGeneration` (an `Arc<AtomicU64>` shared with the running chain), MilkDrop's `generation` (mirrored to the render side's atomics) and the slot list's `scroll_generation_id` (a per-widget fade timer).
- **Every `shell_task` result is session-stamped** (the gate itself is in CLAUDE.md): the generation is a `StaleDropGen` bumped by every login in `handle_login_result` and carried forward by `reset_session_state`. `handle_session_expired` also returns early off the Home screen, so a burst of rejections toasts and wipes the login form once. A task built on a bare `Task::perform` over a shell handle is outside the gate: a result that can act on the session (a `SessionExpired`, a reload, a toast) goes through `shell_task`.
- **One add per playlist at a time**: `append_songs_to_playlist_task` (quick-add, the picker's Add and the add-conflict confirm's Add / Add anyway) checks the playlist's tracks, then writes, so two adds in flight would both pass the check and add a song twice. `Nokkvi::playlist_appends` (`PlaylistAppendQueue`, `src/state/playlist_appends.rs`) runs one add per playlist id, and only on the Home screen (an add marked busy outside a session would never be sent, so nothing would free it); another waits and starts from `handle_playlist_append_finished` once the running one's outcome lands (every outcome is wrapped in `Message::PlaylistAppendFinished`), so its check sees that add. Tickets carry forward across logout. Each add carries a `DuplicatePolicy`, decided by the pure `plan_append` once the tracks are read: `Ask` (quick-add, the picker) opens the confirm on a hit, `Skip` (the confirm's checked box) writes only what is missing AT ADD TIME, so a song another add put there while the confirm was open is skipped too, `AddAll` ("Add anyway", or the box unchecked) writes everything unread. A new add path goes through that task with a policy.
- **PagedBuffer pagination guard** (CLAUDE.md `PagedBuffer<T>`): `Nokkvi::load_paged` (`update/loader_target.rs`) owns the `set_loading(true)` + `needs_fetch` gate for paged views, so a paged view fetches through it; `PaginatedFetch::from_common()` only bundles the request params.
- **PagedBuffer generation**: `generation()` bumps on every mutation. Use `(query, generation)` keys when memoizing filtered results.
- **One seek in flight, the rest merged**: every seek producer (slider, capsule, MPRIS, Previous's rewind, the IPC verb, the seek keys) goes through `Nokkvi::dispatch_seek` → `SeekState` (`src/state/seek.rs`). A relative onto a relative adds, an absolute replaces, a relative shifts a queued absolute. The relative arithmetic lives in `PlaybackController::seek_relative` under ONE engine-lock acquisition — the UI's whole-second `playback.position` freezes while a seek holds that lock, so `position + delta` would land a burst of repeats as a single jump.
- **The seek epoch drops a pre-seek tick**: `PlaybackStateUpdate.seek_epoch` is captured synchronously in `handle_tick` and gates exactly THREE position-derived effects in `handle_playback_state_updated` — the player-bar clock write (`playback.position`; the lyric clock is deliberately ungated, see "The lyric clock is not the position"), `track_listening_time`, and the MPRIS position push. Do NOT widen it to the whole update: a held seek key bumps the epoch ~25x/s against 10 Hz ticks, so the title, duration, gapless prep and queue highlight would freeze on the old track for as long as the key is held. `SeekApplied` carries its dispatch epoch too, so a result from a session cleared mid-flight is dropped rather than clearing a live seek's in-flight flag.
- **No listening credit while a seek is in flight**: `track_listening_time` resyncs `last_position` and credits nothing. A relative seek cannot write its target ahead of time the way `handle_seek` does, and a tick can land between the engine finishing a seek and `SeekApplied` arriving.
