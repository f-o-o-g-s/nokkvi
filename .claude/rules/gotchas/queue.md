# Gotchas: Queue & Indices

## Queue & Indices

- **Queue rows are addressed by `entry_id` (per-row `u64`), not indices, not `track_number`**: `track_number` is a 1-based queue-position label stamped at backend-projection time (`build_queue_song_ui_view_data` in `data/src/backend/queue.rs`). It drifts the moment the UI applies an optimistic local mutation, and stays stale until the backend re-projection arrives. Every path that names an existing queue row carries its `entry_id`; the one index-addressed write is Shift+↑/↓ (`move_queue_item(from, to)`, blocked while a search is active). The Focus path mirrors: `FocusCurrentPlaying` / `FocusOnSong` carry `u64` and the handler does `position(|s| s.entry_id == eid)` — never compare `track_number`. `MoveItem` (single-row drag) carries `source_entry_id` snapshotted at pick time — a mid-drag viewport shift (playback auto-follow) or reload can't re-resolve it to a different row — plus a live drop index `to` (`to == len` appends past the last row); the handler captures the backend target as `MoveBatchTarget::AboveEntry`/`End` BEFORE the optimistic reorder shifts indices, then persists via `move_queue_batch_by_entry_ids`, same as `MoveBatch`.
- **`handle_queue` reads rows by borrow**: the slot indices it resolves are relative to the rows the view shows (filtered under a search). It keeps an owned list (`filtered_owned`) only when a search produced one and otherwise borrows `library.queue_songs` through the field path, which stays disjoint from `&mut self.queue_page`, so a message costs O(viewport). Derive `rows` where it is read (a `&mut self` call ends the borrow), and refresh `filtered_owned` in any arm that changes the search, the order, or (under a search) the rows. A new arm follows the same shape.
- **Batch reorders go through `move_block_before`** (`nokkvi_data::utils::reorder`): the queue's `MoveBatch` arm and the playlist editor's batch drop resolve their pick-time entry_ids to live positions in one `HashSet` pass, then move the block in one more (O(n + k), rows moved, never cloned; proptest-pinned against the old remove/insert loop). The backend's `move_batch_by_entry_ids` resolves and moves the same way under the queue write guard, so the optimistic mirror and the queue run one algorithm. A new multi-row reorder calls it too.
- **Stale multi-selection across refreshes**: `handle_queue_loaded` and `apply_queue_sort` clear `selected_indices` + `anchor_index`. Without this, indices kept pointing at whatever rows occupied those positions after a consume-mode auto-advance / external refresh — different songs.
- **Three sources of truth for "what's playing"**: the queue play cursor (`current_order`, from which `current_index()` is derived), `QueueNavigator.current_song_id`, and the engine's active source. The remove path uses `decide_removal_aftermath` (pure) → `PlaybackController::apply_removal_aftermath` to keep all three in sync; never bypass it, with the one exception below. History append is intentionally skipped on remove (the song was deleted, not skipped past). The decision's `RemovalTransport` classifies the engine through `RemovalTransport::from_engine`, which takes the UI's active station URL (`remove_queue_entries` is passed `ActivePlayback::radio_station()`'s `stream_url`; the engine's own `stream_is_infinite` lags a station start) AND the engine's live source: a station owns the engine only while the engine's source IS its stream, because `ActivePlayback::Radio` is cleared only by `guard_play_action` and so outlives the stream whenever a cold-start Play or a dropped station moves playback into the queue. (The reverse also exists: the guard remembers the station in `PlaybackState::station_left_for_play` and bumps `play_attempt`; a `queue_play_task` play that fails while the engine's source is still that station sends `QueuePlayFailedOnStation`, which restores radio mode only for the play whose own guard left the station and only if no newer play has started. So guard inside the branch that plays, never ahead of a builder: an earlier guard makes the builder's play look like it didn't leave the station. Logout forgets the station.) Under `StreamingRadio` the plan is always `RetargetNavigator`, which points the navigator at the cursor's song and leaves the engine's source and transport untouched, so removing the navigator's row can no longer swap a queue song in under the station's name and emptying the queue can no longer stop the stream. Clear Queue (Shift+D, `nokkvi clear-queue`) follows the same rule: `AppService::clear_queue` takes the same station URL, classifies through `RemovalTransport::from_engine` under the engine lock it stops under, and skips the stop + source clear under `StreamingRadio`; either way it points the navigator at no song. It returns a `ClearQueueOutcome`, and the UI clears the visualizer only on `EngineStopped` (`handle_queue_cleared`), never ahead of the verdict.
- **Remove Duplicates is decided in the backend, from the live cursor**: `AppService::remove_queue_duplicates` → `QueueManager::remove_duplicates` picks the rows under the queue lock (rule: `nokkvi_data::utils::dedupe::duplicate_entry_ids`) and keeps the cursor row as its song's copy, so playback never follows the queue and the path skips `decide_removal_aftermath` (that plan keys on the navigator's song, which can differ from the cursor's and would stop a station or reload the engine); it only resets the gapless prep. The UI mirrors the dropped entry_ids on `QueueLoaderMessage::DuplicatesRemoved` rather than guessing: `queue_current.entry_id` lags a track change. Every batch removal bottoms out at `remove_entries_by_ids`: one pass, one save.
- **Progressive queue generation**: `ProgressiveQueueAppendPage` chains check `progressive_queue_generation` (a `ProgressiveQueueGeneration`, an `Arc<AtomicU64>` whose clones share the counter) before each page AND again inside the page task after the fetch, so a page in flight when the queue is replaced is dropped, not appended. Every queue replacement bumps it: `cancel_progressive_queue_load()` from `enter_new_playback_context()` and clear queue, and the server pull from inside `AppService::pull_queue`'s `before_replace` hook (only when the server returned entries). The header's "X of Y" reads `LibraryData::queue_loading_total()`, which hides a target whose chain is no longer current, so an async bump needs no follow-up message. Logout carries the counter forward. An in-queue play (`QueueAction::PlaySong`, Queue-view roulette) leaves the chain running.
- **Play button cold-start**: resolves the focused (highlighted) row via `common.get_center_item_index`, as Enter does, and plays its `entry_id` via `play_entry_from_queue` — not `queue_songs.first()`, not `track_number - 1`.
- **One play-a-queued-row body**: `PlaybackController::play_entry_from_queue` records history, moves the cursor (re-anchoring the shuffle unless the engine is Playing, `should_reanchor_for_play`) and loads. `play_song_from_queue` (Append & Play's index path) resolves its row to an `entry_id` and goes through it; a new path that plays a queued row does the same, never a copy.
- **Gapless re-peek on mutation**: a queue mutation between gapless prep and the completion callback's `decide_transition` (`services/playback.rs`) calls `clear_queued()`. The transition path always re-peeks — `peek_next_song()` re-computes `queued` when it was cleared, then `PeekedQueue::transition()` consumes it — so the mutation can't strand the transition.
- **Queue sort label is demote-only**: `apply_queue_sort` is the SOLE promoter of the sort dropdown's applied state; `revalidate_queue_sorted()` (on `Nokkvi`) re-verifies the live order against the applied mode and only demotes to the grayed "Unsorted" placeholder. It runs from `handle_queue_loaded` and after every in-place reorder (drag, batch drag, Shift+arrow move) — any new in-place queue mutation must call it or the dropdown lies about the order.

## Transitions

- **Track-completion lock**: the navigator releases its lock across engine I/O during track completion — do not re-introduce a held lock.
- **Repeat track replay**: `decide_transition` replays repeat-track by re-loading the same row (`TrackTransitionPlan::LoadFresh` or `PlayPrepared`, not a seek to start), except under consume, where consume wins and the queue drains. Manual skip (next/prev) bypasses repeat-track (`get_next_song` in `services/queue/navigation.rs`).
